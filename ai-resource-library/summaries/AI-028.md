## 1. What This Resource Teaches  
This guide explains how to evolve a Claude “skill” from a single static markdown prompt into a modular, self‑correcting system. It introduces three complementary techniques: a “gotcha” log that records recurring errors, a folder‑based organization that leverages Claude’s progressive‑disclosure capability, and a constraint‑driven prompting style that supplies intent rather than rigid step‑by‑step scripts. Together, these practices let Claude remember past failures, keep the active context window lean, and adapt its output to edge cases without breaking.

The underlying architecture treats a skill as a lightweight project: a root `SKILL.md` file that contains the core prompt plus a “Gotcha Section,” and optional sub‑directories (`scripts/`, `examples/`, `templates/`, `references/`) that hold auxiliary assets. When Claude processes a request, it first reads the root file, then pulls in any referenced file only if the current task demands it. The gotcha list is consulted at the start of each run, allowing Claude to pre‑empt previously observed mis‑behaviors. The prompting style emphasizes “why” a rule exists (e.g., avoid jargon for a non‑technical audience) instead of prescribing exact phrasing, which yields more resilient outputs.

## 2. Why It Matters  
In production‑grade AI‑assisted workflows, prompt brittleness and context overload are common failure points. By logging mistakes, the system creates a feedback loop that reduces the need for manual post‑processing. The folder‑centric layout prevents the prompt from being flooded with irrelevant data, preserving token budget and improving response latency. Finally, constraint‑oriented instructions enable Claude to handle unforeseen inputs gracefully, cutting down on repetitive re‑prompting and increasing overall throughput. Collectively, these tactics raise the reliability of Claude‑driven automation to a level comparable with custom‑coded solutions, while retaining the flexibility of a language model.

## 4. Key Concepts & Principles  

- **Gotcha Log**: A structured list inside the main prompt that records concrete errors (e.g., “do not start with a greeting”). Claude reads this list at the beginning of each execution, preventing recurrence of the same fault.  
- **Progressive Disclosure**: Claude only loads supplemental files when the prompt explicitly references them, keeping the active context window minimal and focused on the task at hand.  
- **Constraint‑Based Prompting**: Instead of hard‑coding every step, the prompt supplies the rationale behind each rule (e.g., “avoid technical jargon because the audience is non‑technical”), allowing Claude to adapt while still respecting the intended boundaries.  
- **Skill as a Folder**: Treating a skill as a directory rather than a single file encourages modularity. Scripts, example outputs, templates, and style guides live side‑by‑side, making it easy to swap or extend components without rewriting the core prompt.

## 6. Practical Use Cases & Workflows  

### Use Case 1 – Consistent Business Report Generation  
1. **Create the skill skeleton**:  
   ```bash
   mkdir report‑skill && cd report‑skill
   mkdir scripts examples templates references
   touch SKILL.md
   ```  
2. **Populate `examples/`** with a well‑crafted report (`good‑output.md`) and a deliberately flawed version (`bad‑output.md`).  
3. **Add a template** (`templates/report‑template.md`) that defines sections such as Executive Summary, Findings, and Recommendations.  
4. **Write the core prompt** in `SKILL.md`, referencing the template and examples, and include a Gotcha Section that bans opening salutations and mandates ending after the final bullet.  
5. **Run the skill** via Claude’s API, passing the task description (e.g., “Summarize Q3 sales data”). Claude reads the prompt, pulls the template, and produces a report that respects tone and structure.  
6. **Iterate**: If Claude adds an unwanted conclusion, add a specific entry to the Gotcha Section (“Do not add a conclusion unless asked”). Subsequent runs will omit it automatically.  

### Use Case 2 – Adaptive Customer Support Drafts  
1. **Set up the folder** `support‑drafts` with subfolders `templates/` (containing a ticket‑response template) and `references/` (holding a style guide).  
2. **Define constraints** in `SKILL.md` such as “use a friendly tone for consumer‑facing replies” and “avoid technical jargon unless the ticket indicates a developer audience.”  
3. **Add a Gotcha entry** after the first run if Claude inserts a generic “Thank you for contacting us” line that the team prefers to omit.  
4. **Invoke the skill** with the ticket text; Claude reads the prompt, applies the constraints, and only loads the template if the ticket requires a structured response.  
5. **Review and augment** the Gotcha list whenever a new pattern of error emerges (e.g., misuse of pronouns). Over time the skill self‑corrects, reducing manual editing.
