## 1. What This Resource Teaches  
The guide presents a structured, repeatable process for turning an AI‑generated “done” claim into verifiable evidence. It introduces five mandatory checkpoints—**Requirement**, **Test**, **Regression**, **Diff**, and **Unproven**—that must accompany every code change. By embedding these checkpoints into the AI’s workflow (via rule files or hooks), the model is forced to produce concrete artifacts rather than vague confidence statements. The material also covers how to prompt the model for each checkpoint on demand, how to combine them into a single prompt, and how to enforce them automatically with PostToolUse hooks or a dedicated regression sub‑agent.  

The core mechanics revolve around *persistent rule files* (`CLAUDE.md`, `.cursor/rules`, `AGENTS.md`) that the AI reads at session start, *prompt templates* that elicit precise evidence, and *automation hooks* that run tests and regression checks without human intervention. The architecture is intentionally lightweight: it relies on the AI’s own output and the local test harness, avoiding external orchestration tools.  

## 2. Why It Matters  
In modern AI‑augmented development, a model can claim a task is complete simply because the code compiles or the diff looks reasonable. This superficial “confidence” can mask subtle bugs, regressions, or incomplete requirements. By demanding explicit evidence for each checkpoint, the guide transforms the AI from a *confidence‑reporter* into a *proof‑generator*. This yields several strategic benefits:

- **Reduced post‑deployment failures**: Regression checks catch side‑effects before they reach production.  
- **Higher developer trust**: Concrete test outputs and diff rationales make it easier to audit AI work.  
- **Scalable quality assurance**: Automation hooks mean the checks run on every edit, eliminating manual oversight.  
- **Clear accountability**: The Unproven section forces the model to admit uncertainty, preventing blind spots.  

Overall, the methodology aligns AI‑generated code with industry best practices for continuous integration and verification.

## 4. Key Concepts & Principles  
- **Requirement**: The exact user story or specification that the change is intended to satisfy.  
  *Why it matters*: Prevents scope creep and ensures the AI’s output aligns with the original intent.  

- **Test**: The actual execution of a test case and the raw output produced.  
  *Why it matters*: Provides objective evidence that the change behaves as expected, not just a description of expected behavior.  

- **Regression**: Identification of all code paths, files, or routes that could be affected by the change, along with evidence that they still function correctly.  
  *Why it matters*: Guards against hidden side‑effects that surface only under specific conditions.  

- **Diff**: A file‑by‑file justification for each modification, explaining why the change was necessary.  
  *Why it matters*: Detects accidental or unnecessary edits and clarifies intent.  

- **Unproven**: A candid admission of any aspect that could not be verified, with specific reasons.  
  *Why it matters*: Keeps the audit trail honest and highlights areas that require manual review or future testing.

## 6. Practical Use Cases & Workflows  
- **Use Case / Workflow 1: Automatic Verification in a CI Pipeline**  
  1. Add the five‑check rule block to `CLAUDE.md` (or the equivalent file for your tool).  
  2. Configure a PostToolUse hook that runs `npm test` (or your test command) immediately after the AI edits a file.  
  3. When the AI finishes a change, the hook automatically populates the **Test** section with the real output.  
  4. A separate regression sub‑agent scans the repository for dependent modules and reports back the **Regression** section.  
  5. The CI job fails if any of the five sections are missing or contain placeholders.  

- **Use Case / Workflow 2: Manual Prompt‑Based Evidence Collection**  
  1. After the AI signals “DONE,” the developer issues the combined prompt:  
     ```
     Before I accept this as done, give me REQUIREMENT, TEST, REGRESSION, DIFF, and UNPROVEN.  
     ```  
  2. The AI returns a structured block with each section populated.  
  3. The developer reviews the output, verifies the test logs, and checks the diff rationales.  
  4. If any section is empty, the developer asks for clarification or additional evidence.
