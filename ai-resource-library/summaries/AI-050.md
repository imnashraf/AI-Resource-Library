## 1. What This Resource Teaches
This resource introduces "Loop Engineering," a paradigm shift in AI-assisted development where the user transitions from interactive, turn-by-turn prompting to designing autonomous, self-correcting systems. The core educational objective is to teach developers how to construct closed-loop workflows within Claude Code that operate on a defined goal, execute work, verify results against objective criteria, and iterate until success or a budget limit is reached. It moves beyond simple command execution to system architecture, emphasizing the separation of duties between the agent performing the work and the mechanism verifying it.

The technical mechanics focus on integrating four distinct components into a cohesive pipeline: **Automations** (headless execution via CLI), **Worktrees** (isolated parallel environments), **Skills** (reusable procedural knowledge), and **Subagents** (specialized workers with isolated context windows). The guide details how to wire these together using specific CLI flags and file structures, enabling the creation of unattended jobs that can run in parallel, handle complex migrations, or perform scheduled maintenance without human intervention.

Architecturally, the resource frames the AI agent not as a chatbot, but as a worker node in a distributed system. It teaches the user to define "stopping conditions" and "verification checks" as first-class citizens of the workflow. By establishing a clear distinction between the "doer" and the "grader," the guide ensures that the resulting loops are robust, preventing the common failure mode where an AI hallucinates success because it is grading its own output.

## 2. Why It Matters
The strategic value of Loop Engineering lies in its ability to scale AI utility beyond the limits of human attention. Traditional prompting is linear and synchronous; the user is the bottleneck. Loops are asynchronous and parallel; the system is the bottleneck. This shift allows a single developer to manage multiple concurrent AI sessions, effectively multiplying their throughput. As highlighted by the anecdote of merging 150 pull requests in a day, this approach transforms the developer's role from "coder" to "orchestrator," enabling the completion of large-scale, repetitive, or batch-oriented tasks that would be impractical to handle manually.

Efficiency gains are realized through the elimination of context-switching and repetitive instruction. By encapsulating procedural knowledge in "Skills" and isolating work in "Worktrees," the system reduces cognitive load and prevents file conflicts. Furthermore, the inclusion of automated verification (tests, linters, or reviewer agents) ensures a higher baseline of quality, as the loop only terminates when objective criteria are met. This reduces the time spent on manual code review for routine changes, allowing human engineers to focus on architectural decisions and complex problem-solving.

In the context of modern AI workflows, this resource is critical for teams looking to integrate LLMs into CI/CD pipelines or long-running background processes. It provides the blueprint for moving from "AI as a tool" to "AI as an autonomous worker," which is essential for maximizing the ROI of enterprise AI subscriptions and handling the volume of code generation expected in the next generation of software development.

## 4. Key Concepts & Principles
- **The Loop Triad (Goal, Check, Stop)**: A valid loop requires three elements: a declarative end-state (Goal), a verifiable condition that cannot be faked (Check), and a hard limit on resources or iterations (Stop). If the check is subjective or missing, the system degrades into a standard prompt. The "Check" must be external to the agent doing the work to ensure integrity.
- **Separation of Doer and Grader**: A fundamental principle of trust in autonomous systems. The subagent that executes the code changes must be distinct from the agent or process that verifies the changes. This prevents "self-confirmation bias" where an AI might claim a task is complete without actually passing the tests or linters.
- **Context Isolation via Worktrees**: Using Git worktrees allows multiple AI agents to operate on the same repository simultaneously without file conflicts. Each agent gets its own branch and directory, enabling parallel processing. This is critical for "fanning out" work across many files or tasks, as it prevents one agent's edits from corrupting another's context.
- **Procedural Memory via Skills**: Skills are reusable, file-based instructions (Markdown + YAML) that define *how* to perform a task. Unlike prompts, which are ephemeral, skills are persistent. They allow the loop to maintain consistent behavior across runs without the user having to re-explain conventions, styles, or specific steps every time. The description field acts as a trigger for the AI to load the skill only when relevant.

## 5. Tools & Technologies Mentioned
- **Claude Code (CLI)**: The primary execution environment. Specifically, the headless mode (`claude -p`) is used to run non-interactive sessions. Key flags include `--allowedTools` (to restrict permissions), `--max-turns` (to cap iterations), and `--output-format json` (for programmatic parsing of results).
- **Git Worktrees**: A Git feature that allows multiple working directories to be linked to the same repository. In this context, it is used to create isolated sandboxes for parallel AI agents. The `.worktreeinclude` file is used to ensure untracked files (like `.env`) are copied into new worktrees.
- **Claude Skills (`.claude/skills/`)**: A directory structure for storing reusable instructions. Each skill is a folder containing a `SKILL.md` file with YAML frontmatter (name, description) and Markdown body. These are loaded dynamically by the agent based on task relevance.
- **Claude Subagents (`.claude/agents/`)**: A directory structure for defining specialized agents. Each agent is a Markdown file with frontmatter defining its name, description, and allowed tools. Subagents have their own context windows and cannot spawn further subagents, preventing recursive loops.
- **Cron / Scheduled Tasks**: System-level schedulers used to trigger the headless Claude Code commands. This enables "unattended" loops that run on a schedule (e.g., nightly builds or morning checks) without manual intervention.

## 6. Practical Use Cases & Workflows
- **Automated Codebase Migration (e.g., Renaming APIs)**:
    1.  **Define Goal**: "Update all usages of `oldApi` to `newApi` in the `src/` directory."
    2.  **Create Skill**: Write a `SKILL.md` detailing the specific mapping rules and edge cases for the migration.
    3.  **Create Subagent**: Define a `migrator` agent with `Edit` and `Read` tools, and a `reviewer` agent with `Bash` (for running tests) and `Read` tools.
    4.  **Configure Worktree**: Use `claude --worktree migration` to isolate the changes.
    5.  **Execute Loop**: Run `claude -p` with the goal, instructing it to use the `migrator` for changes and the `reviewer` to run tests. Set `--max-turns` to a safe limit.
    6.  **Verify**: The loop continues until the `reviewer` confirms tests pass. If it fails, the `migrator` retries with the error context.

- **Nightly Documentation & Linting Sweep**:
    1.  **Define Goal**: "Ensure all public functions in `lib/` have JSDoc comments and pass ESLint."
    2.  **Create Skill**: A `doc-check` skill that outlines the required JSDoc format.
    3.  **Schedule**: Add a cron job that runs `claude -p "Run doc-check on lib/" --permission-mode dontAsk` at 2:00 AM.
    4.  **Isolation**: The command runs in a temporary worktree to avoid interfering with the main branch.
    5.  **Output**: The agent commits the changes to a `docs-auto-update` branch.
    6.  **Human Review**: The developer reviews the PR in the morning, merging only if the changes are correct. This offloads the tedious "fix lint errors" task to the overnight loop.

## 7. Prerequisites
- **Proficiency with Git**: Deep understanding of branches, worktrees, and conflict resolution is essential, as the workflow relies heavily on parallel branch management.
- **Claude Code Installation**: The user must have the Claude Code CLI installed and authenticated. Familiarity with the interactive mode is assumed before moving to headless mode.
- **Basic Shell Scripting**: Ability to write simple scripts to chain commands, parse JSON output, and set up cron jobs or scheduled tasks.
- **Understanding of CI/CD Concepts**: Familiarity with concepts like "pass/fail" checks, linters, and test suites, as these form the backbone of the "Check" component in the loop.
- **API/Plan Limits Awareness**: Understanding that loops consume significantly more tokens/turns than single prompts. Users must be comfortable setting budget caps to avoid excessive cost.
