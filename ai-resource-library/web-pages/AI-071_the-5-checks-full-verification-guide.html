Chapter 01: Why This Matters More Than It Sounds

Claude, Codex and Cursor will all tell you something is done because the code compiles and the change looks reasonable, not because it was actually tested. That's not the model lying: it's the model reporting confidence as if it were evidence. The fix isn't trusting it less, it's asking it to show its work in a way that can't be faked with a sentence.

Tip: If an agent's answer to "did you test it" is a paragraph and not an output, that's your signal.

The five sections every DONE claim needs

Requirement

the exact requirement, quoted or paraphrased.

Test

the actual test run and its actual output, not a description.

Regression

what this change could affect, and what was checked.

Diff

every changed file and the specific reason it needed to change.

Unproven

anything that couldn't be verified. Never omitted.

Chapter 02: Step 1, Make It Automatic, Not Something You Remember

Don't rely on typing these five checks in every session. Put the rule where the tool reads it automatically.

For Claude Code, add this to your CLAUDE.md (project root or ~/.claude/CLAUDE.md for every project):

Never report a task as done from implementation alone. Before saying DONE,
provide:

REQUIREMENT: the exact requirement this change addresses, quoted or paraphrased
from what was asked.

TEST: the actual test run and its actual output, not a description of what
should happen.

REGRESSION: which existing behaviour could this change affect, and what you
checked to confirm it still works.

DIFF: every changed file and the specific reason it needed to change.

UNPROVEN: anything you could not verify. If nothing is unproven, say so
explicitly rather than omitting the section.

Do not use the word "done" or "complete" without all five present.
Cursor

The same block goes in .cursor/rules (or .cursorrules on older setups).

Codex

It goes in AGENTS.md at the repo root: Codex reads this automatically at the start of a session, the same way Claude Code reads CLAUDE.md.

Tip: Keep it under the five points above. The longer a persistent rule file gets, the more of it gets ignored under pressure. This one rule earns its place at the top.

Chapter 03: Step 2, The Prompts For Each Check, On Demand

Even with the rule in place, some sessions need a manual nudge, especially long ones where context has drifted. These are the exact prompts.

1. REQUIREMENT

"Quote the exact requirement this change was supposed to satisfy. If you inferred anything I didn't explicitly ask for, flag it separately."

Tip: this catches scope creep. Agents regularly implement the version of the task they assumed, not the one you wrote. Quoting forces the gap into view.

2. TEST

"Run the actual test for this now and paste the real output. Not what you expect it to say, the output."

Tip: if there's no test for the behaviour yet, the correct answer is "no test exists for this, here's one I've written and run", not a description of manual reasoning dressed up as testing.

3. REGRESSION

"List every function, file or route that calls or depends on what you just changed. For each one, tell me what you did to confirm it still behaves correctly."

Tip: this is the one people skip because it takes longest. It's also the one that actually prevents the 2am production bug. Worth the extra thirty seconds.

Chapter 03 (continued): The Prompts, Continued

4. DIFF

"Go file by file through the diff. For each file, one sentence on why the change in that specific file was necessary. If you can't justify a file, remove the change and re-check."

Tip: agents sometimes touch files that weren't part of the task because it was easier than isolating the change properly. This prompt surfaces that.

5. UNPROVEN

"What could you not verify with certainty. Be specific, not just 'the integration' but which part of it, and why you couldn't confirm it."

Tip: a vague UNPROVEN is almost as useless as no UNPROVEN. "Couldn't verify the API integration" tells you nothing. "Couldn't verify the webhook fires correctly in production because I don't have access to the live endpoint" tells you exactly what to check yourself.

Chapter 04: Step 3, The One Prompt Version

For when you just want to run all five at once, paste this after any DONE claim:

Before I accept this as done, give me REQUIREMENT (what was actually implemented,
quoted), TEST (the real command you ran and its real output), REGRESSION (what
you checked and how), DIFF (every changed file and why), and UNPROVEN (anything
you couldn't confirm, specifically). If any section would be empty, say so, don't
skip it.

Chapter 05: Step 4, Make It Enforce Itself

This is the part most people don't know exists. Claude Code supports hooks: small scripts that run automatically on an event, like right after Claude edits a file. You can set a PostToolUse hook that runs your actual test suite automatically every time Claude finishes editing code, so the TEST section isn't something Claude chooses to do: it's something that happens whether it wants to or not.

Tip: This matters because a persistent rule in CLAUDE.md is a strong suggestion: the model can still forget it under a long context window. A hook is not a suggestion, it runs regardless of what the model decides.

You can also spin up a separate subagent whose only job is the REGRESSION check, a second Claude instance that goes and reads what depends on the changed code and reports back, so the regression check isn't done by the same agent that's motivated to say everything's fine.

Tip: If you're not ready to set up hooks or subagents yet, the CLAUDE.md rule from Step 1 gets you most of the way there on its own. Add the enforcement layer once the manual version becomes second nature.

Chapter 06: Common Ways This Still Gets Faked

Even with all of the above, watch for these patterns: they're the most common way "evidence" turns out not to be evidence.

✕
Test output that's suspiciously clean

If every test passes on the first run with zero output noise, ask to see the full terminal output, not a summary of it.

✕
Regression checks that only look at the changed file

A real regression check looks at what calls that file, not just the file itself.

✕
UNPROVEN sections that are technically true but strategically vague

"Couldn't verify edge cases" is not an UNPROVEN, it's a way of avoiding one.

✕
Diff explanations that describe what the code does instead of why it changed

"This function handles user auth" is not a justification for why it was touched.

Closing: Ask For Evidence. Not Confidence.

Quick Recap To Save

  • Put the five-check rule in CLAUDE.md, .cursorrules or AGENTS.md depending on your tool, so it runs by default.
  • Use the five prompts individually when a session needs a manual check.
  • Use the one combined prompt when you want everything at once.
  • If you're comfortable going further, a PostToolUse hook and a dedicated regression subagent take this from "asked for" to "guaranteed."
  • Watch for clean-looking evidence that isn't actually evidence.
