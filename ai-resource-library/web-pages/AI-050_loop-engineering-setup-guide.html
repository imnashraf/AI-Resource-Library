Loop Engineering

Max Johnson AI Agency Founder · @maxjohnscn

The head of Claude Code stopped writing prompts. Now he hands Claude a goal and builds a loop that runs until it's done. Here's the shift, and the four pieces you need to build your first loop inside Claude Code.

Note

Everything here runs inside Claude Code, the command-line and desktop tool, not the chat box. You don't need to write traditional code to start; a loop begins as a clear brief the agent follows. One thing to know upfront: loops run several agent turns per item, so they use more of your plan than a single prompt. Start with small batches.

The Shift

For two years, getting work out of a coding agent meant writing a good prompt. You typed a thing, read what came back, typed the next thing. The agent was a tool and you held it the whole time, one turn after another. Boris Cherny, the head of Claude Code at Anthropic, the person who built it, says that part is over for him.

"I don't prompt Claude anymore... My job is to write loops."

Boris Cherny, Head of Claude Code, Anthropic

By his own account he hasn't hand-written production code in months. On one record day he merged 150 pull requests. He runs five to ten Claude sessions at once, and his main development machine is his phone. The numbers grab the headlines, but they aren't the point.

The point is the change in posture. Instead of holding the tool turn by turn, you build a small system that finds the work, hands it out, checks it, records what's done and decides what's next, then you let that system poke the agent instead of you. That practice now has a name: loop engineering.

The Old Way
  • Prompt, read, prompt again
  • You're in the loop for every turn
  • One task at a time
  • The work stops when you stop
The Loop
  • A goal in, a finished result out
  • The system runs the turns, not you
  • Many tasks at once, in parallel
  • It keeps going while you're away

What a Loop Actually Is

A prompt is one instruction you babysit. A loop is a goal plus the machinery to chase it without you. Three things have to be true before you actually have a loop, and not just a prompt with extra steps.

1. A goal, not a prompt. You describe the end state ("every public function has a docstring") not the keystrokes to get there. The agent works out the steps.

2. A check it can't fake. Something verifiable decides "done": the tests pass, the linter is clean, a second agent approves. The one rule everyone building these agrees on: the agent doing the work must never grade its own work.

3. A stopping condition. The loop runs until the check passes, or until a budget (turns, cost or items) runs out. A fuzzy goal gives it nothing to check, so it just stops like an ordinary prompt.

Goal
the end state you want
›
Work
agent attempts it
›
Check
verify against the goal
›
Done
check passes
fails the check → back to Work
Tip

If you can't name how you'd check the result, you don't have a loop yet, you have a prompt. Define the check first; everything else hangs off it.

Piece One: Automations

The part that runs without you in the room.

Claude Code has a headless mode. Instead of opening the interactive session, you pass the goal on the command line with -p: one prompt in, one result out to stdout, then it exits. No window to watch, no clicking. That's the engine a loop wraps around, you can fire it from a script, from CI, from a git hook, or on a schedule.

Headless: one goal in, one result out
claude -p "Add docstrings to every public function in src/.
Run the tests. Only stop once they pass." \
--allowedTools "Edit,Read,Bash(npm test)" \
--max-turns 40 \
--output-format json

The flags are your control panel. --allowedTools pins exactly what it may touch. --max-turns and a budget cap are the circuit breakers that stop a loop running forever. --output-format json hands you a clean result you can pipe straight into the next step. For fully unattended runs, add --permission-mode dontAsk so it never pauses to ask.

To make it recurring, you don't sit and re-run it. A cron entry, or a scheduled task on Anthropic's own infrastructure, fires the same command every morning, so the loop kicks off on its own and the result is waiting when you look.

Tip

Always cap turns and budget before you walk away. An uncapped loop is how you come back to a job that ran all night and a bill to match. Caps first, ambition second.

Piece Two: Worktrees

Two agents, same repo, zero collisions.

Run two Claude sessions on the same folder and they overwrite each other's work. A git worktree fixes this: each session gets its own working directory on its own branch, while sharing the same repository history. It's built into Claude Code, so one agent can build a feature in one place while another fixes a bug in another, neither touches the other's files.

Each command opens an isolated, parallel session
claude --worktree feature-auth  # branch: worktree-feature-auth
claude --worktree fix-checkout  # a second, no conflicts

# each lands in .claude/worktrees/<name>/

The desktop app creates a worktree for every new session automatically. For loops, the real power is pairing this with subagents: add isolation: worktree to an agent's settings, or simply ask Claude to "use worktrees for your agents", and every parallel agent gets its own throwaway worktree that's cleaned up when it finishes. That's what lets one loop fan out across a dozen tasks at once.

Watch For

A worktree is a fresh checkout, so untracked files like .env aren't carried over. Add a .worktreeinclude file (it uses .gitignore syntax) to your project root and Claude copies those files into every new worktree automatically.

Tip

Worktrees isolate the files. Subagents (next chapter) divide the work. A loop that runs wide needs both, one without the other either collides or bottlenecks.

Piece Three: Skills

Stop explaining the same goal over and over.

A skill is a folder with a SKILL.md file: a little block of YAML at the top (a name and a description) and your instructions in plain Markdown below. Write down how you want something done once, and Claude pulls it in automatically whenever it's relevant. No more pasting the same context into every session. Skills live in .claude/skills/ for a project, or ~/.claude/skills/ for everywhere.

.claude/skills/pr-checklist/SKILL.md
---
name: pr-checklist
description: Use before opening any pull request.
  Runs lint and tests and checks the changelog is updated.
---
When preparing a PR:
1. Run the linter and fix what it flags
2. Run the full test suite. Do not open the PR if it fails
3. Confirm CHANGELOG.md has an entry for this change

Here's the part that matters: at startup Claude only reads the name and description of each skill. It loads the full file only when the description matches what you're doing. So the description is the whole game, write it as "use when..." and be specific, or it won't fire at the right moment. And you don't have to write skills by hand; ask Claude to create one for you.

Tip

In a loop, skills are the standing instructions. The goal changes each run, the skill keeps the how constant, so you're not re-teaching the agent every single time it goes around.

Piece Four: Subagents

Send Claude off on its own, and get the result back.

A subagent is a separate worker with its own context window. The main session hands it a job, it goes away and does it, and it returns just the result, so your main context stays clean. The format is the same as a skill: a Markdown file with frontmatter and a system prompt. They live in .claude/agents/ (project) or ~/.claude/agents/ (personal), and you can create one with the /agents command or just write the file.

.claude/agents/test-runner.md
---
name: test-runner
description: Runs the test suite and reports failures.
  Use proactively after any code change.
tools: Read, Bash
---
You run tests and report results. Run the suite, then list
only the failures with the file and line. Do not fix anything.

The description is the routing hint, it's how the main agent decides to hand work off, so be specific about when to use it. Omit tools and it inherits the session's tools; list them to keep it tight. And by design a subagent can't spawn its own subagents, that's deliberate, it stops a loop from spiralling into runaway recursion.

Tip

Keep the doer and the grader separate. A subagent that does the work should never be the one that approves it, spin up a second reviewer agent for the check. That separation is what makes the loop trustworthy.

Wiring It Into One Loop

None of the four pieces is the loop on its own. The loop is what you get when you stack them:

A
Automations are the engine

claude -p on a schedule, it runs with nobody watching.

S
Skills are the standing instructions

How the work gets done, the same way, every time round.

U
Subagents are the hands

One finds the work, others do it, a separate one checks it.

W
Worktrees are the lanes

So the hands work in parallel without ever colliding.

Put together, a run looks like this: the schedule fires, the main agent reads the goal, spawns subagents in their own worktrees, each does its task using your skills, a separate reviewer checks the result against the goal. Pass and it commits or opens a PR, fail and it goes back round, until the check passes or the budget runs out. You can stand up a first version with nothing more than a plain-English brief.

A starter loop charter, paste into Claude Code and fill the brackets
You are running a loop, not answering once.
GOAL: [the end state you want, must be checkable]
EACH RUN: take the next item, do the work in its own worktree,
  then have a separate reviewer agent check it against the goal.
DONE WHEN: [the verifiable condition is met]
STOP IF: you pass [N] items, or the check fails twice.
Use my [skill name] for how the work should be done.
Start Small

A loop runs several agent turns per item, so it uses your plan faster than a single prompt. Keep the [N] items cap low on the first run, watch one full cycle, then widen it once you trust the check.

When To Build A Loop

A loop costs setup and burns more usage than a prompt. That trade pays off on some work and wastes your time on the rest. Know which is which before you build.

Build a Loop For
  • Repeating work across many items, every file, every endpoint
  • Anything with a clear pass or fail check
  • Migrations and large batched changes
  • Overnight or scheduled work you'd rather not babysit
  • Tasks worth the setup and the extra usage
Just Prompt For
  • A single answer you need once, write this, explain that
  • Work with no verifiable "done" state
  • Quick edits and one-off questions
  • Exploration where you want to stay in the driver's seat
  • Anything faster done by hand than wired up
The Tell

If you've run the same kind of prompt five times today, tweaking it a little each time, that's a loop waiting to be written. The repetition is the signal, stop tweaking and define the goal and the check.

You're Not Prompting Anymore.

Pick one repeating task. Write the goal and the check. Wrap it in claude -p, give it a skill and a reviewer subagent, run it in a worktree, then step back and let it go. That's the whole shift: from holding the tool, to building the thing that holds it.
