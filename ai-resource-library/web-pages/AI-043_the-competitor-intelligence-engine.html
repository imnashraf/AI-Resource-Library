Chapter 01: The Service We Sold

The first thing we sold a paying client was not a document and not a set of prompts. It was a system that runs on its own. Every week it pulls down what the client's competitors are posting, works out what is winning and why, finds the openings nobody is covering, and hands back a brief plus a batch of content drafts written in the client's voice. They open one page and it is all there.

That distinction is the whole reason it sells. A prompt pack is something the client could half-build themselves on a free afternoon. Infrastructure that scrapes, stores, analyses and produces on a schedule is not. It takes a real stack, real wiring, and someone who can build it. That is what they are paying for, and it is why this is a service rather than a tip.

Chapter 02: The Architecture

Six layers, one direction of flow. Each layer does one job and hands clean data to the next. Build them in order, every layer is testable on its own before you connect it.

Layer 1Ingestion Scrape competitor posts & comments on a schedule (Apify)
↓
Layer 2Store Normalise to one schema, dedupe, persist (Supabase)
↓
Layer 3Analyse Classify & score every post into structured JSON (Claude API)
↓
Layer 4Detect gaps Aggregate the week, surface the whitespace (Claude API)
↓
Layer 5Generate Draft content in the client's voice from the gaps (Claude API)
↓
Layer 6Deliver Brief + drafts to the client, on a schedule (n8n, Notion)

Chapter 03: Layer 1 - Ingestion

You do not build scrapers from scratch. Apify has maintained "actors" for every platform that already handle proxies and blocking. You point them at competitor handles and they return structured post data. The two you will use most:

  • IG apify/instagram-scraper: posts, captions, likes, comments, media URLs (~$1.50 / 1K results)
  • TT clockworks/tiktok-scraper: videos, views, likes, shares, comments (~$1.70 / 1K results)

Run them from n8n with the Apify node set to "Run Actor", with "Wait for finish" on so results flow to the next node. Fire one actor run per platform in parallel, never chain platforms inside one run, or one failure takes down the rest.

Normalise at ingest, not at query time: Every actor returns different field names. Map them to one shared schema the moment data lands, keep the raw payload too, and dedupe on platform + post id.

Supabase: Posts Table

posts (
  post_id text primary key,
  platform text,         -- instagram | tiktok
  author_handle text,
  posted_at timestamptz,
  text text,             -- caption / script
  metrics jsonb,         -- {likes,comments,shares,views}
  raw jsonb,             -- full actor output, kept
  analysis jsonb         -- filled by Layer 2
)
-- dedupe: unique (platform, post_id)
NoteScrape public data only, keep request volumes sane, and prefer official platform APIs where they exist. Set the cadence to what the client needs, weekly is plenty for content intelligence and keeps cost and risk low.

Chapter 04: Layer 2 - Analysis

Raw posts are noise until they are labelled. This layer sends every new post to the Claude API and forces a structured verdict back, the same fields on every row, so the data is queryable. Use tool use to lock the output to a JSON schema rather than parsing free text.

Per-Post Analysis: Structured Output

POST api.anthropic.com/v1/messages
model: claude-sonnet-4-6
system: "Competitor content analyst. Score one post."
(cache_control: ephemeral - caches the rubric)

// returned JSON, stored to posts.analysis
{
  "hook_type": "contrarian | listicle | story | ...",
  "format": "reel | carousel | static",
  "topic": "...",
  "pillar": "tutorial | concept | social_proof | founder",
  "engagement_score": 0-100,
  "why_it_worked": "one sentence"
}

The Model Strategy That Keeps Cost Down

  • Claude Haiku: a cheap first pass that filters junk and obvious low performers
  • Claude Sonnet: the per-post analysis above, run over everything that clears the filter
  • Batch API: send the week's posts async for a 50% discount; cache the rubric to save more
TipScore engagement relative to each account's own baseline, not in raw likes. A post that beats its own author's median is the real signal, a 50k account and a 5k one are not comparable head to head.

Chapter 05: Layer 3 - Gap Detection

Now every post is labelled and scored, the system can reason across the whole set instead of one post at a time. A weekly job aggregates the analysed rows and asks the harder question: what is winning, and what is nobody covering?

The whitespace is where comment demand is high but coverage is low, the questions the audience keeps asking that no competitor has turned into a proper post. That is the client's opening, and it is computed, not guessed.

Weekly Intelligence Brief: Output

{
  "top_patterns": [ {hook, format, pillar, avg_score} ],
  "rising": [ "topics accelerating week-on-week" ],
  "fading": [ "topics losing engagement" ],
  "gaps": [
    { "topic": "...",
      "demand": "high comment volume, few posts",
      "angle_for_client": "the post to make" }
  ],
  "recommended_mix": { "tutorial": "40%", "concept": "30%",
    "social_proof": "15%", "founder": "15%" }
}

Claude (use the deeper model here, since it is one call a week) reads the aggregated data and returns this brief. It becomes the first thing the client sees, and the input to Layer 4.

Chapter 06: Layer 4 - Content Generation

The last intelligence layer turns the gaps into drafts, in the client's voice, not generic AI voice. The trick is a voice profile built once from the client's best existing posts, then pinned as a cached system prompt on every generation call so it never drifts and never re-costs.

Generation Call

system: /voice/profile.md  // cached
sentence length, tone, words used,
words never used, how they open + close

user: "Write 3 drafts for this gap from the brief:
[gap.topic] + [gap.angle_for_client].
Use the winning hook pattern [pattern].
Reel script format. Mapped to pillar: [pillar]."

// stored to a drafts table, status = pending_review

What Comes Out

  1. A batch of scripts and hooks mapped to the week's gaps and the recommended pillar mix
  2. Each tied back to the competitor post it learned from, so the client sees the reasoning
  3. All marked pending review, the client approves, edits, or rejects before anything is theirs
TipBorrow the structure of winning competitor posts, never the words. The engine fills a proven shape with the client's angle and language, that is the line between learning from a market and copying it.

Chapter 07: Layer 5 - Orchestration & Delivery

n8n is the conductor. One scheduled workflow runs the whole pipeline end to end, with no one touching it. The node sequence:

  1. Schedule Trigger: weekly, Monday 06:00
  2. Supabase: fetch the competitor handle list
  3. Apify Run Actor x2: Instagram + TikTok, in parallel, wait for finish
  4. Code node: normalise to the shared schema, dedupe
  5. Supabase: upsert the new posts
  6. Claude (Batch): analyse every new post, write the result back
  7. Code node: aggregate the week, score the gaps
  8. Claude: write the intelligence brief, then the content drafts
  9. Notion + Slack: deliver the brief and drafts to the client

The Client-Facing Layer: For a premium tier, have Claude Code build a small Next.js dashboard on top of Supabase: the competitor feed, the weekly brief, and a one-click approve / reject on every draft. It turns a delivery into a product the client logs into.

Chapter 08: Building It With Claude Code

Claude Code is the operator's tool, a terminal agent that writes, runs and tests the system against real data. It is the difference between this being a month of engineering and a few focused days. The build sequence:

  1. Scaffold the repoA TypeScript project with the Anthropic SDK, a Supabase client and an Apify client. Claude Code lays out the structure and the env config.
  2. Connect the MCP serversAdd the Supabase and Apify MCP connectors so Claude Code can create tables and test scrape runs itself, without you leaving the terminal.
  3. Build ingestion & analysisClaude writes the schema migration, the normalise / dedupe logic, the analysis calls with the JSON schema, and the gap scoring, then runs it on real rows.
  4. Build the dashboard, then deployOptional Next.js dashboard on Supabase, then Claude wires it to a host (Railway or a VPS) and you point n8n's schedule at it.
