Three Things That Separate Basic Claude Users From Everyone Else.

Most people using Claude skills are working with a single markdown file and hoping for the best. These three things change what a skill actually is, from a static prompt to something that learns, stays organised, and works intelligently every time you invoke it.

What you will have when this is done:

  • A gotcha section that logs mistakes and prevents them from repeating
  • A proper folder structure that keeps your context window clean
  • Instructions that guide Claude without trapping it
Gotcha Section
Logs every mistake. Claude reads it before the next run. Mistakes don't repeat.
Folder Structure
Skills are folders, not files. Progressive disclosure keeps your context window clean.
Context not Scripts
Constraints + intent beats rigid step-by-step. Claude adapts; it doesn't break.

Step 01, Build a Gotcha Section, The part most people skip

A gotcha section is a dedicated list inside your skill file that logs every mistake Claude has made while using it. Every time Claude does something wrong, wrong format, wrong tone, ignored a constraint, you add it to the list. The next time the skill runs, Claude reads the list first. The mistake does not repeat.

Add this section to the bottom of your SKILL.md file:

## Gotcha Section # Things Claude has done wrong using this skill. # Each entry is specific. Vague entries do not work. - Never use bullet points inside the executive summary. Use short paragraphs only. - Do not open with 'Great question!' or any variation. Start directly with the answer. - Do not add a conclusion section unless explicitly asked. The output ends after the final point.

TIP: The gotcha section only works if the entries are specific. 'Be more professional' does nothing. 'Do not use exclamation marks in business writing' works every time.

NOTE: Every time you use the skill and Claude makes a mistake, add it immediately while it is fresh. The list builds up over time and the skill gets noticeably better within a few sessions.

Step 02, Use the File System Properly, A skill is a folder, not a file

Most people put everything in one markdown file. A properly structured skill is a folder. Scripts, templates, examples, and references all live alongside the prompt in subfolders, and they do not clutter your context window because Claude uses progressive disclosure. It only pulls a file in when the task actually needs it.

Structure your skill folder like this:

mkdir my-skill mkdir my-skill/scripts mkdir my-skill/examples mkdir my-skill/templates mkdir my-skill/references # Your main prompt file touch my-skill/SKILL.md

Then reference the subfolders inside your SKILL.md so Claude knows they exist:

## Available Resources - scripts/format.py, use this when formatting output as a table - examples/good-output.md, reference this for tone and structure - templates/report-template.md, use this for any report output - references/style-guide.md, consult this for brand voice questions

TIP: You do not need all four folders on day one. Start with examples/, drop in one good output and one bad output and reference them. That alone will improve consistency immediately.

NOTE: Progressive disclosure means Claude reads your SKILL.md first and only opens a subfolder file if the current task requires it. Your context window only ever contains what is relevant right now.

Step 03, Give Context and Constraints, Not Scripts, Stop railroading Claude

Instructions that are too rigid make a skill brittle. When Claude is told exactly what to do at every step, it cannot handle edge cases and output becomes robotic. The fix is to give Claude the context behind each rule and define constraints rather than scripts. Claude follows intent far better than it follows rigid commands.

The difference in practice:

Too rigid, breaks on edge cases:

Step 1. Always write exactly 3 bullet points. Step 2. Use this exact sentence structure every time. Step 3. Never deviate from the template under any circumstances.

Adaptive, works every time:

Use bullet points for lists of 3 or more items. Use prose for fewer than 3 items. Write in a direct, plain-English tone. Avoid jargon unless the audience requires it. Follow this structure as a guide. Adapt if the content genuinely requires it.

TIP: When writing a constraint, ask yourself: does this rule tell Claude what to do, or why to do it? The why produces better results. 'Avoid jargon because this audience is non-technical' beats 'do not use technical words'.

WARNING: If you are correcting Claude on almost every run, the problem is not Claude, it is the skill. Overly rigid instructions produce inconsistent output. Loosen the script and tighten the constraints.

All Three Together, What You Now Have

Each of these three things is useful on its own. A gotcha section that prevents repeated mistakes. A file system that keeps context clean. Instructions that let Claude think rather than just follow.

Running all three together is what most people building with Claude are not doing. The skill learns over time, handles edge cases without breaking, and pulls in exactly the resources it needs for each task.

TIP: The fastest way to get started is to take a skill you already use, add a gotcha section to the bottom of it, and run it three times. By the third run you will have two or three entries in the gotcha list and the output will already be noticeably more consistent.
