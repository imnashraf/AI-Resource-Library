Chapter 01, Dead Links, Broken Images & Missing 404 Pages

When someone navigates to a URL that doesn't exist in your app, a deleted product, a mistyped link, a shared URL that's moved, they hit a blank screen or a raw browser error. That's the first impression. A custom 404 page tells the user where they are, that the app is working fine, and gives them a way back.

The Problem
  • Links in your UI pointing to routes that don't exist yet
  • Images referencing assets that weren't uploaded or have moved
  • No 404 route, so the user gets a blank screen or a browser default
The Fix

Ask Claude Code to build a custom 404 page for your framework. It should match your app's design, display a clear message, and include a button back to the homepage. Also ask it to audit all img tags and internal links for broken references.

Prompt for Claude Code
"Build a custom 404 page for this application that matches the existing design system.
Add a friendly error message and a 'Go Home' button. Then audit all internal links and
image sources in the codebase and flag any that are broken or missing."

Chapter 02, Bugs You Don't Know About

Your app has bugs right now. Every app does. The question is whether you find them before your users do. Without error tracking, the first signal you get is a one-star review or a support message. With error tracking, you get the full crash trace automatically, with everything you need to fix it.

The Problem
  • Errors and crashes happen silently, you have no visibility
  • Users leave without telling you what went wrong
  • By the time you hear about a bug, you can't reproduce it
The Fix

Sentry is the standard tool for this. It captures every unhandled error and exception, records the full stack trace, the user's browser, the page they were on, and the sequence of actions that led to the crash. Free tier covers most early-stage apps.

Prompt for Claude Code
"Set up Sentry error tracking in this application. Install the Sentry SDK, initialise it
with a DSN I'll provide, and make sure all unhandled errors and promise rejections are
captured automatically. Show me where to add the DSN."

After setup: take the full Sentry error report, paste it directly into Claude Code, and ask it to fix the issue. The trace gives Claude exactly what it needs.

Chapter 03, Forms That Don't Handle Errors

Long form. User fills it in. Hits submit. Nothing happens, or worse, an error wipes everything they've typed. They're not going to fill it in again. This is one of the most common and most damaging UX failures in early apps, and it's entirely preventable.

The Problem
  • Form state isn't preserved when a backend call fails
  • No inline validation, errors only surface after submit
  • Submission state gives no feedback (no loading indicator, no error message)
  • On failure, the user has no idea what went wrong or what to do next
The Fix

Your frontend needs to be resilient regardless of what the backend does. Form state should live in the client until the submission fully succeeds. Every field should validate inline. Every submission should have a clear loading, success, and error state.

Prompt for Claude Code
"Review all forms in this application. For each one: preserve form state on failed
submissions, add inline field validation with error messages, and implement loading,
success, and error states on the submit button. Make sure no user data is lost if the
backend call fails."

Chapter 04, Broken Loading States

A slow network call hits. The screen freezes. Or worse, a spinner appears and just keeps spinning with no indication of whether anything is happening. The user doesn't think "the backend is taking a second." They think the app is broken. They leave.

The Problem
  • UI doesn't update when a network call is in progress
  • No visual difference between loading, failed, and empty states
  • Failed calls leave the UI in a frozen or misleading state
  • No way for the user to retry when something goes wrong
The Fix

Every async operation needs three explicit states handled in the UI: loading (something is happening), error (something went wrong, here's what to do), and empty (the call succeeded but there's nothing to show). On top of that, skeleton loaders give a better experience than spinners, and every error state should include a retry button.

Prompt for Claude Code
"Audit all async data calls in this application. For each one, implement three UI states:
loading (skeleton loader where appropriate), error (with a user-friendly message and a
retry button), and empty (a helpful empty state, not a blank page)."

Chapter 05, The Blank White Screen

One component throws a JavaScript error. Without an error boundary, React (or your framework) stops rendering the entire component tree. The user sees a completely blank white screen. They have no idea what happened. There's no way back except refreshing the page, and they're not going to bother.

The Problem
  • A single component crash takes down the entire application UI
  • No fallback, user sees a blank screen with no message or action
  • Error is invisible unless you have Sentry set up (see Chapter 02)
The Fix

An error boundary wraps a section of your component tree. When a component inside it throws, the boundary catches the error and renders a fallback UI instead, a simple message and a reset button. The rest of the app keeps working normally.

Prompt for Claude Code
"Add error boundaries to this application. Wrap the top-level app component with a global
error boundary that shows a 'Something went wrong, please try again' message and a reset
button. Then add more granular error boundaries around any major sections or data-fetching
components."

React note: Error boundaries are class components or use the react-error-boundary package. Claude Code will handle the implementation either way.
