Chapter 1: Why One Model Isn't Enough

The Core Idea

Every AI model has a perspective shaped by its training. That perspective has gaps. The gaps you can't see are the dangerous ones.

Most people who use AI for coding settle into a pattern quickly: open Claude Code, describe the problem, work through it together. It feels thorough. The model reasons carefully, asks clarifying questions, and produces polished output. What could be missing?

Quite a lot, it turns out. Not because any single model is bad, but because every model is trained differently. Claude is exceptional at reasoning about intent and holding complex context. But the patterns it leans on, the error classes it's most sensitive to, the edge cases it tends to anticipate, all reflect its training data and reward signals. OpenAI's coding models reflect a different set. Google's models reflect another.

When you work with only one model, you don't just get one perspective on your code. You also get one set of blind spots. And because the model is fluent and confident, those blind spots are invisible. You have no signal that something was missed.

The echo chamber problem

This is subtler than it sounds. The risk isn't that a single model gives you wrong answers. It's that it gives you consistently wrong answers in the same direction. A model that misses a class of race condition will miss it every time you ask about threading. A model that tends to underestimate memory pressure will do so reliably. You can iterate for hours within that blind spot and never escape it, because your feedback loop is entirely contained within the model's own frame.

A second model with a different training lineage breaks that loop. It may disagree with the first on exactly the thing the first was confident about. That disagreement is a signal. It tells you there's something worth looking at more carefully.

The context window problem

There's a second failure mode that compounds the first. Most coding models have context windows that cap out well below the size of a real production codebase. Ask Claude Code to reason about a 300,000-token monorepo, and it will work within what it can hold, making educated inferences about the rest. That's often enough. Sometimes it isn't.

Gemini's context window is built at a different scale: around 1 million tokens. For the tasks where full-codebase visibility genuinely matters, that difference is decisive. Rather than swapping tools every time you hit a size constraint, you can route those specific tasks to Gemini from within the same session.

What you get from three models working together

The setup in this guide doesn't replace your judgment. It amplifies it. Claude Code drives the session and handles the bulk of the building work. Codex CLI acts as a reviewer with a different perspective on logic and execution paths. Gemini CLI handles the tasks that need a wider view, whether that's a very large codebase, a long document, or a task that needs multiple passes across a lot of material at once.

You don't have to manually shuttle files between three terminal windows. The PAL MCP server, covered in Chapter 5, handles the coordination. You stay in Claude Code and describe the work. The routing happens underneath.

Chapter 2: Meet Your AI Team

Why This Matters

Knowing what each model is genuinely best at determines when you route work to it. Using the wrong model for a task doesn't just waste time. It means you're trusting a weaker signal on something that matters.

Before you start routing tasks across three models, it helps to understand what each one is actually built for. The descriptions below are not marketing copy. They're the operational picture of each tool that shapes how you'll use it day to day.

Claude Code
The Builder

Strongest at reasoning about intent, holding context across large codebases, and making coherent changes across many files at once. The natural choice to drive the overall session.

Codex CLI
The Reviewer

Runs on OpenAI's coding models, trained heavily on real execution paths. Particularly sharp at spotting logical errors and edge cases that pass tests but break in production.

Gemini CLI
The Analyst

Built on Gemini's huge context window, around 1 million tokens. The one you hand a massive monorepo, a long video, or a 200-page PDF that the others can't hold in one pass.

Claude Code in practice

Claude Code is where you'll spend most of your time. It understands natural-language instructions well enough that you can describe what you want at a high level, and it will make coherent decisions about implementation without you specifying every detail. It holds context across a session reliably, so earlier decisions inform later ones. It's also the model that has the deepest integration with your local file system through its MCP tooling.

For the workflows in this guide, Claude Code acts as the coordinator. It decides when to call Codex or Gemini and passes them the right context for each task.

Codex CLI in practice

Codex CLI is OpenAI's command-line coding tool. It runs locally, connects to your terminal, and can execute code as well as reason about it. The model it runs on has been trained with heavy emphasis on real-world code execution: the kinds of patterns that appear not just in open-source repositories, but in the paths code actually takes at runtime.

Where Codex earns its place in this setup is in post-build review. After Claude Code has made a set of changes, routing those changes through Codex gives you a second opinion from a model that approaches the code from a different angle. It catches different things. That's the value.

Gemini CLI in practice

Gemini CLI is Google's command-line tool for Gemini models. Unlike the other two, its primary advantage is not a different reasoning style. It is scale. A 1 million token context window means you can hand it an entire large codebase, a long transcript, or a dense PDF and ask questions that require synthesizing information across all of it simultaneously.

For individual developers working on real projects, this is useful in a specific but important set of situations: analyzing a very large codebase you've just inherited, reviewing a long set of dependency changes, or cross-referencing a large document against your current implementation.

Chapter 3: What You Need & Installing The CLIs

Note

Check every prerequisite before you start. Installing the PAL MCP server in Chapter 5 will fail silently if Node.js, Git, or Python are missing or on the wrong version.

This chapter covers two things: confirming you have the right starting point, and getting all three CLI tools installed on your machine. The checklist below is the full set of prerequisites. Each item has a reason attached.

Installing Codex CLI

Codex CLI is installed via npm. It requires Node.js 20 or higher. Run this in your terminal:

npm install -g @openai/codex

After it finishes, verify the install with:

codex --version

You should see a version number. If you see a "command not found" error, check that your npm global bin directory is on your PATH.

Installing Gemini CLI

Gemini CLI is also distributed via npm. Install it with:

npm install -g @google/gemini-cli

Then verify:

gemini --version

Again, a version number means it installed correctly. If you're on a machine with multiple Node.js versions managed by nvm or similar, make sure you're running Node.js 20+ before installing.

Verifying Node.js and Git

If you're not sure which version of Node.js you have, check it:

node --version
git --version

Both commands should return version numbers. If Node.js is below 20, upgrade it before continuing. The most reliable way to manage Node.js versions is with nvm on macOS and Linux, or nvm-windows on Windows.

Installing uv for Python

uv is a fast Python package manager used by the PAL MCP server. Install it with:

# macOS and Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# Windows (PowerShell)
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"

Restart your terminal after installation, then verify:

uv --version
python --version

Python should report 3.10 or higher. If it reports a lower version, you'll need to install a newer Python before proceeding to Chapter 5.

Chapter 4: Sign In With Your Existing Subscriptions

Note

None of these tools require an API key if you're using a qualifying subscription. API key authentication is available as an alternative, but this guide covers the subscription path because it's simpler and included in what you already pay for.

Each of the three CLIs authenticates separately. The steps below take around two minutes in total. Do them in order, making sure each one succeeds before moving on.

01
Sign in to Codex CLI with ChatGPT

Run codex in your terminal and choose Sign in with ChatGPT when prompted. This opens a browser window: log in with the ChatGPT account that holds your Plus, Pro, Business, Edu, or Enterprise plan. Codex usage then runs against your plan's included usage, not pay-as-you-go API credits.

02
Sign in to Gemini CLI with Google

Run gemini in your terminal. On first run you'll be asked how to authenticate: choose Login with Google and sign in with your personal Google account. This unlocks Gemini's free tier, which is generous enough for most individual workflows.

03
Claude Code is already signed in

If you're already using Claude Code day to day, there's nothing extra to do here. It authenticates the same way it always has.

If You'd Rather Use API Keys

Both Codex CLI and Gemini CLI support API key authentication as an alternative. Set OPENAI_API_KEY in your environment for Codex, and GEMINI_API_KEY for Gemini. When these variables are present, the CLIs use them instead of the browser-based login flow. If you go this route, API usage is billed at standard rates against your OpenAI or Google Cloud account, not your subscription plan.

Confirming each login worked

Before continuing, run a quick test prompt in each CLI to confirm authentication is working. Open a new terminal tab for each:

# Test Codex CLI
codex "What is 2 + 2?"

# Test Gemini CLI
gemini "What is 2 + 2?"

Both should respond with something sensible. If either returns an authentication error, go back through the sign-in steps for that tool before proceeding.

Chapter 5: Install The PAL MCP Server

The Core Idea

PAL stands for "Proxy AI Layer." It's a free MCP server that exposes Codex CLI and Gemini CLI as tools that Claude Code can call directly from inside a session. Without it, coordinating three CLIs means three separate terminal windows and manual copy-paste. With it, Claude Code handles the routing.

The PAL MCP server is an open-source project. You install it once and configure Claude Code to connect to it. After that, the three CLIs behave like a single coordinated system.

Clone the repository

First, clone the PAL repo to a stable location on your machine. The PAL server runs as a persistent background process, so put it somewhere you won't accidentally delete it:

git clone https://github.com/pals-ai/pal-mcp-server.git ~/.pal-mcp
cd ~/.pal-mcp

Install dependencies

PAL uses uv to manage its Python dependencies. With uv installed from Chapter 3, run:

uv sync

This reads the project's dependency file and installs everything into an isolated virtual environment. It does not affect your global Python installation.

Configure Claude Code to use PAL

Claude Code looks for MCP server configurations in its settings file. Open or create ~/.claude/claude_desktop_config.json and add the PAL server entry:

{
  "mcpServers": {
    "pal": {
      "command": "uv",
      "args": [
        "--directory",
        "/Users/YOUR_USERNAME/.pal-mcp",
        "run",
        "pal-server"
      ]
    }
  }
}

Replace /Users/YOUR_USERNAME/.pal-mcp with the actual path where you cloned the repo. On Windows, use a path like C:\\Users\\YOUR_USERNAME\\.pal-mcp with double backslashes.

What This Gives Claude

Once this configuration is in place, Claude Code gains two new tools it can call mid-session: pal_ask_codex and pal_ask_gemini. These let Claude pass a question or task directly to Codex CLI or Gemini CLI and receive the response back in the same session thread. You don't need to describe the routing in your prompts. Claude decides when to use each tool based on what the task calls for.

Restart Claude Code

After saving the config file, restart Claude Code completely. On the next launch, it will start the PAL server automatically and connect to it. You should see a small indicator in the Claude Code interface confirming MCP servers are active.

Chapter 6: Verify It's Working

Don't assume the setup is working. Verify it explicitly before you rely on it for real work. This chapter gives you three tests that confirm each layer of the stack is functioning correctly.

Test 1: Confirm PAL tools are available

Start a new Claude Code session and ask it directly what tools it has access to:

What MCP tools do you currently have available? List them.

In the response, you should see pal_ask_codex and pal_ask_gemini listed among the available tools. If you don't see them, the PAL MCP server did not start correctly. The most common cause is a path error in claude_desktop_config.json. Double-check the directory path and restart Claude Code again.

Test 2: Trigger a Codex handoff

Ask Claude to use Codex explicitly for a simple task:

Use Codex to review this function and tell me if there are any edge cases:

function divide(a, b) {
  return a / b;
}

Claude should call pal_ask_codex, pass the function to Codex CLI, and return Codex's response alongside its own. You'll see the tool call appear in Claude's response thread. If you only see Claude's own analysis with no tool call, the PAL connection isn't working. Check the Claude Code logs for error messages.

Test 3: Trigger a Gemini handoff

Test the Gemini route with a question that benefits from its context capacity:

Use Gemini to summarize what you know about large context window use cases in AI development.

Claude should call pal_ask_gemini and return the response. If this works, all three layers of the stack are functioning.

If It Doesn't Trigger

Claude will use its own judgment about when to call PAL tools, even when asked. If it answers from its own knowledge instead of calling the tool, rephrase to be more explicit: "Call pal_ask_gemini with this question." That forces the tool call rather than letting Claude decide it can answer without one. For automated workflows, this explicit phrasing is the more reliable pattern anyway.

Chapter 7: Prompts To Run Your AI Team

Note

The prompts below are starting points. Adapt the specifics to your own codebase and workflow. The underlying pattern, being explicit about which model you want to handle which task, is what matters.

The most effective way to use this three-model setup is to be deliberate about routing from the start. Rather than asking Claude to handle everything and hoping it delegates appropriately, describe the work and specify which model should handle which part.

The dual-review pattern

After Claude Code makes changes to a file, send it for a second pass through Codex:

You've just edited auth.js. Now use Codex to review the changes
for logic errors, off-by-one errors, and any edge cases in the
token validation flow. Return both your own notes and Codex's
findings side by side.

This is the core workflow. Claude builds, Codex reviews. The side-by-side format makes disagreements visible rather than blending them into a single response.

The large-codebase analysis pattern

When you need to understand something that spans the whole project:

Use Gemini to read the entire src/ directory and identify every
place we're directly mutating state outside of a dedicated state
management function. Return the file paths and line numbers.

Gemini's context window is what makes this possible at scale. On a large codebase, asking Claude or Codex to do this would require chunking, which introduces the risk of missing cross-file patterns.

The architecture disagreement pattern

When you're making a significant structural decision and want genuine divergence of opinion:

I'm deciding between approach A and approach B for the caching
layer. First, give me your own recommendation with reasoning.
Then use Codex to evaluate the same two options independently.
Then use Gemini to do the same. Present all three positions
clearly, including any disagreements.

Three models giving independent assessments of the same architectural question is more useful than one model asked to play devil's advocate. The disagreements between them are genuine signals about the tradeoffs in each approach.

The automated review hook

If you want Codex to run automatically every time Claude Code completes a coding task, you can configure this in your CLAUDE.md file. Add an instruction at the top:

# Auto-review rule
After every coding task that modifies or creates a file, call
pal_ask_codex with the changed file contents and the task
description. Append Codex's review to your response under a
heading called "Codex Review."
Note

Adding this instruction to CLAUDE.md makes it a persistent rule for the project rather than something you have to repeat in every prompt. Claude Code reads CLAUDE.md at the start of every session, so the behavior applies automatically from that point forward.

The document analysis pattern

When you have a long spec, RFC, or technical document to work from:

Use Gemini to read the attached architecture spec (spec.pdf) and
extract every requirement that affects the database schema.
Return a numbered list. Then use that list as the basis for
our schema design work.

This takes advantage of Gemini's ability to hold a large document in a single pass, rather than summarizing it in chunks and potentially losing detail in the compression.

Chapter 8: Permissions, Limits & Costs

Why This Matters

Three models running in parallel can consume plan usage faster than expected. Understanding what each model charges for, and what the limits look like in practice, prevents surprises at the end of the billing period.

Before you make this setup a core part of your daily workflow, it's worth being clear about how each tool handles permissions and how costs accumulate.

Claude Code permissions

Claude Code runs with the file system permissions of the user account that launched it. By default, it will ask for confirmation before editing files, running terminal commands, or making network requests. The PAL MCP server runs as a subprocess of Claude Code and inherits the same permissions.

In the Claude Code settings, you can configure auto-approve rules for specific directories or command types. For a development environment where you trust Claude Code to edit files freely, setting auto-approve for your project directory reduces friction significantly. For production environments or repos with sensitive configuration, keep the confirmation prompts on.

Codex CLI permissions

Codex CLI can execute code locally, which means it has real side effects. When PAL passes a task to Codex, Codex can run commands in your terminal environment. Be specific about what you're asking it to do. "Review this function for edge cases" is safe. "Fix this function and run the tests" gives it execution access.

Codex CLI has a sandbox mode that restricts it to read-only operations. For pure review tasks, enabling sandbox mode is a sensible default. You can pass the --sandbox flag when invoking Codex manually, or configure PAL to pass it automatically.

Usage limits by plan

All three tools enforce usage limits based on your subscription tier. The practical limits you'll hit depend heavily on how you use them:

  • Claude Code on Pro or Max has generous included usage. Running Codex reviews on every single file edit will consume usage faster than using it selectively on significant changes.
  • Codex CLI on ChatGPT Plus has a monthly usage cap. Heavy automated review workflows may require a Pro or higher plan to avoid hitting the limit mid-month.
  • Gemini CLI on a free Google account uses Gemini's free tier, which resets daily. For occasional large-context analysis, this is usually enough. For continuous heavy use, consider a Gemini Advanced subscription or API key with billing.

Cost when using API keys

If you switch to API key authentication for either Codex or Gemini (as described in Chapter 4), usage is billed per token at standard rates. This is usually more expensive than a flat subscription for heavy use, but cheaper for light or irregular use. Track your API usage in the provider dashboards during the first week so you can calibrate.

What not to let run automatically

The automated review hook from Chapter 7 is powerful, but attaching it to every file edit is aggressive. In a long Claude Code session with many small changes, you can hit rate limits before the important work is done. A more sustainable pattern is to trigger the multi-model review at meaningful checkpoints: after completing a feature, before committing, or after a major refactor, rather than after every individual edit.
